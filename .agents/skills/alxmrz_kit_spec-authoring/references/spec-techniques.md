# Техника вывода требований и сценариев

## 1. От бизнес-правила к Requirement

Источник требований — наблюдаемое поведение, за которое кто-то отвечает:
пользователь, внешняя система, оператор. Формулируй правило так, чтобы его можно
было проверить, не читая код.

Признак хорошего Requirement:

- в нём одно поведение (а не список из пяти);
- понятен субъект и условие;
- понятно, что считается нарушением;
- нет слов, требующих интерпретации: «корректно», «удобно», «оптимально»,
  «быстро», «надёжно».

Проверка: если инженер может реализовать требование двумя несовместимыми
способами — требование недоопределено. Если требование допускает только одну
реализацию — это уже дизайн, переноси в `design.md`.

## 2. Example mapping

Самый надёжный способ получить полный набор сценариев — разложить правило на
примеры до того, как писать текст.

Порядок:

1. **Правило** — одно предложение «что должно быть».
2. **Примеры** — 3–7 конкретных случаев с настоящими значениями, не «какой-то
   ввод», а `5`, пустая строка, `-1`, `9999999999`.
3. **Вопросы** — случаи, где поведение неочевидно. Их надо задать пользователю,
   а не додумать.
4. **Сценарии** — только после того, как примеры сошлись.

Рабочая таблица:

| Правило | Вход / состояние | Ожидаемый результат | Тип |
| --- | --- | --- | --- |
| Количество принимается только в диапазоне 1–99 | количество `1` | значение сохранено | позитивный |
| | количество `0` | отказ, состояние не изменилось | негативный |
| | количество `100` | отказ, состояние не изменилось | граничный |

Строки с типом «негативный» и «граничный» — это и есть обязательное требование
«минимум один позитивный и один негативный/граничный кейс на правило».

## 3. Эквивалентные классы

Не пиши сценарий на каждое значение ввода. Раздели вход на классы, где поведение
одинаково, и покрой по одному представителю класса плюс переходы между классами.

Пример для количества позиции 1–99:

| Класс | Представитель | Ожидание |
| --- | --- | --- |
| Меньше минимума | `0`, `-5` | отказ |
| В диапазоне | `1`, `99` | успех |
| Больше максимума | `100` | отказ |
| Не число | `abc`, пустая строка | отказ с повторным запросом |

Границы (`1` и `99`) проверяй отдельно от середины диапазона — классическая
ошибка живёт ровно на границе.

## 4. Граничные значения

Для каждого числового или размерного ограничения проверь:

- границу и границу ±1;
- пустое множество (ноль элементов, пустая строка, пустой массив);
- ровно один элемент;
- максимально допустимое значение;
- на единицу больше максимума.

Для темпоральных и повторных действий: первое нажатие, повторное нажатие,
действие после завершения сценария.

## 5. Таблицы решений

Когда поведение зависит от двух-трёх условий сразу, сценарии по одному условию
плодят дубли. Используй таблицу решений, а сценарии выводи из её строк.

| Заказ подтверждён | Позиция на складе | Количество валидно | Результат |
| --- | --- | --- | --- |
| нет | да | да | заказ создан |
| нет | нет | да | отказ «нет на складе» |
| нет | — | нет | отказ «некорректное количество» |
| да | — | — | отказ «заказ уже подтверждён» |

Дальше — по сценарию на строку (или на группу строк с одинаковым результатом),
и таблица же подсказывает, какие тесты писать.

## 6. Именование сценариев

Имя сценария должно читаться как факт о системе, а не как описание действий
тестировщика.

- Плохо: «Проверить ввод», «Тест 1», «Работа с формой».
- Хорошо: «Позиция с нулевым остатком помечается недоступной», «Скидка применяется
  сразу при подтверждении», «Некорректное количество не создаёт заказ».

Формула: `<условие> → <наблюдаемый результат>`, без глаголов в повелительном
наклонении.

## 7. Формулировки

| Плохо | Хорошо |
| --- | --- |
| Система должна быстро отвечать | Система SHALL отвечать на запрос поиска не дольше 100 мс |
| Пользователь может ввести число | Система SHALL принимать количество 1–99 из формы заказа |
| Обрабатывать ошибки корректно | Система SHALL отклонять количество вне диапазона, не меняя сохранённое значение |
| Желательно логировать | (убрать из спеки — это дизайн/эксплуатация) |

`SHALL`/`MUST` — обязательство. `SHOULD` — рекомендация, и её надо обосновать
в спеке. `MAY` — разрешение. Не смешивай уровни в одном требовании.

## 8. Что делать с неопределённостью

Не додумывай молча. По каждому открытому вопросу нужно явное решение
пользователя, записанное в артефакт.

- Влияет на объём работ или наблюдаемое поведение → спрашивай, не двигайся дальше.
- Косметика (порядок секций, формулировка) → прими разумное решение и перечисли
  допущения в `proposal.md` или `design.md`.
- Противоречие с существующей спекой → покажи оба места и спроси, какое главнее,
  прежде чем править.
