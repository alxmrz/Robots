# Трассируемость: сценарий → тест → код

Цель — по любому имени в артефактах однозначно находить реализацию и обратно.
Расхождение имён считается дефектом планирования, а не мелочью.

Все рабочие таблицы этого раздела — изменений, тестов, API и (если меняется
серверный контракт) серверного API — живут в `design.md`. В `spec.md` только
требования и сценарии: таблицы привязаны к именам файлов, классов, методов и
эндпоинтов, а значит описывают реализацию, а не наблюдаемое поведение.

## Цепочка

```
Requirement      «Отклонение некорректной регистрации»
    └── Scenario     «Регистрация с занятым email отклоняется»
          └── TestClass::testMethod   RegistrationTest::testDuplicateEmailThrows
                └── API-строка         App\User\Registration::register(string $email, string $password): User
                      └── Код          src/User/Registration.php
                            └── Диаграмма  design.md, classDiagram: узел Registration
```

Каждое звено должно существовать. Если сценарий есть, а теста в таблице нет —
сценарий не будет проверен. Если тест есть, а сценария нет — непонятно, что он
защищает.

## Таблица изменений

Раздел `design.md`: одна таблица на изменение — в ней расписаны **все**
изменения, которые вносит реализация, — по файлам, классам и методам. По ней
должно быть видно, что именно трогается и что появляется, ещё до открытия кода.

Формат:

| Файл | Класс | Метод (сигнатура) | Действие | Что меняется |
| --- | --- | --- | --- | --- |
| `src/User/Registration.php` | `App\User\Registration` | — | добавляется | Новый класс: регистрация по email и паролю |
| `src/User/Registration.php` | `App\User\Registration` | `register(string $email, string $password): User` | добавляется | Создаёт пользователя, бросает `DuplicateEmail` |
| `src/User/UserRepository.php` | `App\User\UserRepository` | `findByEmail(string $email): ?User` | добавляется | Ищет пользователя по email |
| `src/User/LegacySignup.php` | `App\User\LegacySignup` | `register(array $data): array` | удаляется | Заменён на `Registration::register()` |

Требования:

- **Файл** — путь от корня проекта. Одна строка на изменение, а не на файл:
  файл с пятью правками занимает пять строк.
- **Класс** — полное имя класса (FQCN). Для изменения без класса (конфигурация,
  свободная функция, миграция) — `—`.
- **Метод (сигнатура)** — полная сигнатура: имя, типы параметров, значения по
  умолчанию, возвращаемый тип. Для изменения без метода (новый класс целиком,
  файл конфигурации) — `—`.
- **Действие** — одно из `добавляется`, `изменяется`, `удаляется`.
- **Что меняется** — одно предложение: зачем правка и что она меняет в
  поведении или контракте.
- Изменения уровня класса и файла тоже попадают в таблицу: новый класс — строкой
  с `—` в колонке метода; удаление файла — строкой с `—` в методах.
- Сигнатуры изменяемых методов приводятся в **новой** редакции. Если метод
  меняет сигнатуру, старая редакция указывается в колонке «Что меняется».
- Таблица полная: всё, что появится или изменится в коде в рамках изменения,
  перечислено здесь. Нет строки — нет правки.

## Таблица тестов

Раздел `design.md`: одна таблица на изменение — в неё входят **все** тесты
**всех** модулей, которые добавляет изменение, — не только те, что проверяют
правила этого файла. По ней должно быть видно полный объём предстоящего
тестового кода.

Формат:

| Файл тестов | Тестовый метод | Что проверяет |
| --- | --- | --- |
| `src/tests/User/RegistrationTest.php` | `testDuplicateEmailThrows` | Отклоняет регистрацию с занятым email, бросая `DuplicateEmail::email()` |
| `src/tests/User/RegistrationTest.php` | `testPasswordIsHashed` | Сохраняет пароль только в виде хеша |
| `src/tests/User/UserRepositoryTest.php` | `testFindByEmailReturnsNull` | Возвращает `null`, если пользователь с таким email не найден |

Требования:

- **Файл тестов** — путь к файлу с тестовым классом от корня проекта, в котором
  будет жить этот тест. Несколько тестов одного файла — отдельные строки с
  одинаковым значением в этой колонке. Если файла ещё нет, указывай путь, по
  которому он появится.
- **Тестовый метод** — точное имя метода из кода, включая стиль (`testXxx` или
  атрибут/аннотация — как принято в проекте). Переименование в коде требует
  правки таблицы в той же задаче.
- **Что проверяет** — правило, граница или отказ. Одно предложение.
- Таблица полная: покрывает тесты всех модулей изменения, включая модули из
  соседних спек-файлов этого изменения. Не оставляй за её пределами тест,
  который появится в коде.
- На каждое правило — минимум позитивный и негативный/граничный кейс.
- В таблице нет нереализованных методов и нет реализованных тестов, забытых
  в таблице.

## Таблица API

Раздел `design.md`: итоговый публичный контракт после изменения.

Формат:

| Класс | Публичный метод (сигнатура) | Что делает |
| --- | --- | --- |
| `App\User\Registration` | `register(string $email, string $password): User` | Создаёт пользователя; бросает `DuplicateEmail` при занятом email |
| `App\User\UserRepository` | `findByEmail(string $email): ?User` | Ищет пользователя по email или возвращает `null` |
| `App\User\DuplicateEmail` | `static email(string $email): self` | Создаёт ошибку регистрации на занятый email |
| — | `normalizeEmail(string $input): ?string` | Приводит ввод к нормализованному email или `null` |

Требования к сигнатурам:

- Полная сигнатура: имя, типы параметров, значения по умолчанию, возвращаемый
  тип. Для PHP — с `?`, union-типами, enum-типами и `static` для статических
  методов.
- Конструктор включай: он часть публичного контракта.
- Для свободной функции колонка `Класс` пустая или `—`, функция целиком в
  колонке метода.
- Описание — одно предложение: что делает, какие исключения/ошибки бросает,
  какие побочные эффекты имеет (I/O, изменение состояния).
- Только публичные методы. Приватные и защищённые в таблицу не попадают.

Инвариант: **если метод есть в коде, он есть в таблице; если он в таблице, он
есть в коде.** Таблица — контракт для задач, а не украшение.

Соотношение с таблицей изменений: таблица изменений показывает **дельта-объём**
работы (что трогаем), таблица API — **итоговый публичный контракт** после
изменения. Метод, добавленный в таблице изменений, обязан появиться в таблице
API; удалённый — обязан из неё исчезнуть.

## Таблица серверного API

Раздел `design.md`: если изменение добавляет или меняет серверное API — HTTP/REST,
RPC, SOAP, gRPC, GraphQL, WebSocket, очередь команд или любой другой внешний
контракт, — список добавленных эндпоинтов/операций и их контрактов расписывается
таблицей. Этот вид API не покрывается таблицей API из раздела выше: там публичные
методы классов, здесь — то, что вызывается снаружи процесса.

Таблица обязательна, как только в задаче есть необходимость реализовать
серверное API любого вида. Если API не добавляется и не меняется — оговаривай это
явно, как и отсутствие ER-диаграммы.

Формат:

| Метод/операция | Путь/RPC-имя | Назначение | Запрос | Ответ | Ошибки |
| --- | --- | --- | --- | --- | --- |
| `POST` | `/api/users` | Зарегистрировать пользователя | `email`, `password` | `201`: `id`, `email` | `422` — занятый email, `400` — невалидный ввод |
| `GET` | `/api/users/{id}` | Получить пользователя | path: `id` | `200`: `id`, `email` | `404` — не найден |
| `gRPC` | `UserService/GetUser` | Получить пользователя | `GetUserRequest{id}` | `GetUserResponse{id, email}` | `NOT_FOUND` |
| `SOAP` | `GetUser` | Получить пользователя | `GetUser{id}` | `GetUserResult{id, email}` | `SoapFault` с кодом `NOT_FOUND` |

Требования к контракту:

- **Метод/операция** — глагол протокола (`GET`, `POST`, `PATCH`, RPC-имя, имя
  SOAP-операции), а для протоколов без глагола — тип сообщения.
- **Путь/RPC-имя** — полный путь или имя операции, включая версию API; шаблон
  параметра (`{id}`) показывай явно.
- **Назначение** — одно предложение: что делает вызов.
- **Запрос** — обязательные и опциональные поля с типами, для path/query/header —
  явно указывай, где они лежат.
- **Ответ** — код или тип ответа и ключевые поля; для `void`-ответа пиши «нет
  тела», а не оставляй пустую ячейку.
- **Ошибки** — коды/статусы и условие их возникновения; хотя бы один отказ.
- Аутентификация и авторизация описываются отдельной строкой или колонкой, если
  она есть: без этого контракт неполон.
- Idempotency, лимиты, таймауты, пагинация — там, где протокол их предполагает.
- Версионирование и обратная совместимость фиксируются, если изменение ломает
  существующий контракт.

Полнота и согласованность:

- каждый эндпоинт таблицы имеет обработчик в таблице изменений;
- каждый участник `sequenceDiagram` из внешнего контракта есть в этой таблице;
- коды ошибок таблицы совпадают с поведением сценариев в `spec.md`;
- удалённый эндпоинт исчезает из таблицы, а не помечается «устарел» без срока.

## Имена, которые должны совпадать везде

| Понятие | Где обязано совпасть |
| --- | --- |
| Файл | Таблица изменений в `design.md`, `tasks.md`, файловая структура проекта |
| Класс | Таблица изменений и таблица API в `design.md`, `classDiagram` в `design.md`, `tasks.md`, код |
| Публичный метод | Таблица изменений и таблица API в `design.md`, `sequenceDiagram`/`classDiagram` в `design.md`, код |
| Эндпоинт/операция серверного API | Таблица серверного API в `design.md`, обработчик в таблице изменений, `sequenceDiagram`, код |
| Файл тестов | Таблица тестов в `design.md`, `tasks.md`, файловая структура проекта |
| Тестовый метод | Таблица тестов в `design.md`, `tasks.md`, код |
| Таблица/колонка БД | `design.md` (`erDiagram`), миграции |
| Имя сценария | `spec.md`, `tasks.md` (ссылка «закрывает сценарий X») |

В `spec.md` из этого списка остаются только имена сценариев. Файлы, классы,
методы, тесты и колонки БД в спеке не упоминаются: их место — `design.md`.

## Проверка перед сдачей артефактов

1. Пройди по таблице изменений в `design.md`: каждый файл, класс и метод
   существует в `design.md` или объяснён в «Что меняется».
2. Выпиши все имена из таблицы API и пройди по `design.md`: каждое должно
   встречаться на соответствующей диаграмме.
3. Сверь таблицу изменений с таблицей API: добавленные методы есть в обеих,
   удалённые — ни в одной.
4. Если серверное API меняется: сверь таблицу серверного API с таблицей
   изменений — у каждого эндпоинта есть обработчик, у каждого обработчика —
   строка в таблице серверного API.
5. Выпиши все сценарии и найди каждый в таблице тестов.
6. Выпиши все тестовые методы из таблицы и найди их в задачах.
7. Найди в `tasks.md` упоминания файлов и сверь с файлами из таблицы изменений.
8. Просмотри `spec.md`: нет ли в нём таблиц, файлов, классов, методов, тестов,
   эндпоинтов или диаграмм. Найденное перенеси в `design.md`.
9. Если реализация вынужденно отошла от диаграммы — правится диаграмма и таблица
   изменений в той же задаче, а не задним числом «когда-нибудь».

## Частые поломки

| Поломка | Признак | Лечение |
| --- | --- | --- |
| Дрейф имён | В коде `registerUser`, в таблице `register` | Переименовать или обновить таблицу в той же задаче |
| Тест-дубль | Один метод в двух спек-файлах | Оставить один раз в полной таблице в `design.md` |
| Призрачные тесты | Метод в таблице, класса нет | Реализовать или убрать строку |
| Неполная таблица | Тест есть в коде, но не в таблице | Добавить строку с файлом тестов в той же задаче |
| Незапланированная правка | Файл изменён, строки в таблице изменений нет | Добавить строку или откатить правку |
| Таблица не в том файле | Таблица изменений, тестов, API или серверного API лежит в `spec.md` | Перенести в `design.md` |
| Несогласованные таблицы | Метод есть в таблице изменений, но не в API | Добавить или убрать строку в обеих |
| API без контракта | Эндпоинт есть в коде, но не в таблице серверного API | Добавить строку с запросом, ответом и ошибками |
| Контракт без реализации | Эндпоинт в таблице, обработчика в таблице изменений нет | Реализовать или убрать строку |
| Немая сигнатура | `process($data)` | Уточнить типы или признать, что контракт не определён |
| Диаграмма-фантазия | Узел `UserService`, класса нет | Исправить диаграмму до реализации |
