# Нарезка задач

Цель — такой список задач, который может взять в работу несколько агентов
одновременно без конфликтов по файлам.

## Основная единица

**Одна задача = один связный кусок работы над своим набором файлов или
модулей.** Не «слой», не «этап», не «день недели».

Хорошая задача:

- имеет одного владельца на время выполнения;
- трогает предсказуемый список файлов;
- проверяется изолированно, не дожидаясь остальных;
- закрывает один или несколько названных сценариев;
- содержит свои тесты.

Плохая задача:

- «Реализовать бэкенд»;
- «Написать тесты» (отдельно от реализации);
- «Доделать оставшееся»;
- задача, где перечислено полпроекта файлов.

## Порядок нарезки

1. Выпиши модули из `design.md` (`classDiagram`) — это естественные границы.
2. Найди общий каркас: интерфейсы, типы, контракты, точки входа, конфигурацию.
   Он идёт в задачу-предшественник.
3. Разложи остальное по модулям так, чтобы файлы не пересекались.
4. Для каждой задачи определи зависимости: от каркаса и от других модулей.
5. Для каждой задачи сформулируй изолированную проверку.

## Каркас как задача-предшественник

Все, что нужно всем и не принадлежит никому, выносится вперёд:

- интерфейсы и абстрактные контракты;
- общие типы, enum'ы, доменные исключения;
- автозагрузка, конфигурация сборки, тестовый раннер;
- точка входа-заглушка.

Правило: если два модуля должны договориться о сигнатуре, сигнатура появляется
в каркасе раньше обоих. Иначе они договорятся по-разному.

В `tasks.md` каркас помечается как предшественник, и явно перечисляется, какие
задачи от него зависят.

## Пометка зависимостей

Для каждой задачи нужно понимать, можно ли её брать прямо сейчас.

| Тип | Как выглядит | Что делать |
| --- | --- | --- |
| Независима | «параллельно с группами N, M» | Брать сразу |
| Зависит от контракта | «зависит от контрактов `Registration`, `User` из группы 1» | Можно начинать против сигнатур, не дожидаясь реализации |
| Зависит от реализации | «после группы 2» | Только последовательно |
| Интеграционная | «после групп 1–6» | Последняя, собирает всё |

Зависимость от **контракта** — не то же самое, что от **реализации**. Если
сигнатуры зафиксированы в таблице API, а эндпоинты — в таблице серверного API
(`design.md`), задачу можно писать параллельно, пока другая реализует тело.

## Изолированная проверка

У каждой задачи должна быть команда или действие, доказывающее её готовность без
остальных задач.

Примеры:

- `vendor/bin/codecept run Unit RegistrationTest` зелёный;
- `php bin/console order:place --dry-run` на заглушке печатает план и выходит с кодом 1;
- миграция применяется и откатывается на пустой БД.

Если изолированной проверки нет — задача сформулирована слишком крупно или
слишком завязана на других.

## Тесты в задаче-реализаторе

Тесты пишутся в той же задаче, которая реализует правило. Не бывает
«финальной задачи на тесты»: она гарантирует, что до её наступления правила
живут без проверки, и что при нехватке времени тесты отрежутся первыми.

Ориентир:

- в задаче перечислены точные имена тестовых методов из таблицы тестов;
- задача закрывается только тогда, когда они написаны и проходят;
- добавление нового правила в спеку добавляет и тест, и строку в задаче.

## Шаблон формулировки задачи

```markdown
- [ ] N.M <Что делаем, одним глаголом и объектом>
      Файлы: <точный список>
      Зависит от: <контракты/задачи> (или «независима»)
      Закрывает сценарии: <имена из spec.md>
      Тесты: <TestClass::testMethod, ...>
      Проверка: <команда и ожидаемый результат>
```

Все пять полей нужны: без «Файлов» задача конфликтует с соседней, без
«Проверки» непонятно, когда закрывать, без «Тестов» правило останется без
покрытия.

## Раскладка по группам

Полезно группировать задачи по волнам, чтобы видеть параллелизм:

- **Волна 0** — каркас, одна задача, блокирует всех.
- **Волна 1** — независимые модули, N задач параллельно.
- **Волна 2** — модули, зависящие от контрактов волны 1.
- **Волна 3** — интеграция, сборка, документация, сплошной прогон.

Признак здоровой нарезки: в волне 1 больше одной задачи, и ни одна из них не
трогает файлы другой.

## Частые ошибки

| Ошибка | Последствие | Лечение |
| --- | --- | --- |
| Две задачи правят один файл | Конфликт при параллельной работе | Слить в одну или вынести общую часть в каркас |
| Задача без проверки | Непонятно, закрыта ли | Добавить команду проверки |
| Задача «написать тесты» | Правила без покрытия до конца | Перенести тесты в реализацию |
| Контракт появляется в двух задачах | Несовместимые сигнатуры | Вынести контракт в каркас |
| Задача размером в неделю | Не влезает в один рабочий цикл | Дробить по модулям, не по этапам |
