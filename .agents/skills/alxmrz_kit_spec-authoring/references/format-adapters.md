# Адаптация под формат конкретного фреймворка

Скилл описывает технику. Формат задаёт фреймворк или шаблон проекта. Здесь —
как переносить одно в другое, не изобретая синтаксис.

## Общий принцип

1. Сначала найди источник формата: шаблон артефакта, файл конфигурации правил,
   вывод CLI с инструкциями, существующие артефакты этого проекта.
2. Возьми оттуда обязательные секции, разметку заголовков и операции над
   требованиями.
3. Наполняй эти секции по технике скилла.
4. Если технике не хватает места в формате — не расширяй формат самовольно.
   Скажи, чего не хватает, и предложи правку шаблона.

## Определение формата по признакам

| Признак | Формат | Что делать |
| --- | --- | --- |
| Заголовки вида `ADDED MODIFIED REMOVED RENAMED` | Дельта-спека | Следуй операциям; изменённое требование приводи полностью |
| `Given / When / Then` | Gherkin | Используй его; `Given` — состояние, `When` — действие, `Then` — результат |
| `WHEN / THEN` без `Given` | Упрощённый сценарный | Условие в `WHEN`, проверка в `THEN`, предусловие — отдельной фразой |
| Таблица требований с колонкой ID | Трассируемая спека | Держи ID стабильными при правках |
| Просто список требований | Плоский формат | Один пункт = одно правило; сценарии вложенными подпунктами |
| Отдельный файл на каждую способность | Capability-структура | Один файл = одна способность, не сваливай несколько |

## Дельта-спеки

Читай так:

- `ADDED` — новое требование, полный текст;
- `MODIFIED` — изменённое требование, обязательно целиком в новой редакции
  (не «см. выше»);
- `REMOVED` — удаление, нужны причина и миграция;
- `RENAMED` — только переименование, поведение не меняется.

Ловушка: `MODIFIED` с сокращением. Прочитавший дельту должен понять
итоговое требование, не открывая основной файл.

## Gherkin-совместимые формы

Если формат предполагает `Given/When/Then`:

- `Given` не должно содержать действий, только состояние;
- `When` — ровно одно действие;
- `Then` — наблюдаемый результат, а не реализация;
- `And` используй для продолжения, не для второго независимого сценария.

Правило «одно правило — один сценарий» сохраняется в любом формате.

## Если формат фреймворка противоречит проектному правилу

Пример конфликта: фреймворк требует помещать таблицу API прямо в спеку, а проект
выносит все таблицы в `design.md`.

Порядок:

1. Побеждает проектное правило — оно принято осознанно.
2. Реализуй проектное правило в рамках формата: требования и сценарии остаются
   в спеке, а таблицы изменений, тестов и API идут в `design.md`. Если шаблон
   жёстко задаёт секции спеки, а таблиц там нет — это нормально, ничего
   добавлять не нужно.
3. Озвучь конфликт в ответе или в допущениях артефакта, не скрывай.

## Если фреймворка нет

Пиши по умолчанию: дельта-разметка, сценарии `WHEN/THEN`; таблицы изменений,
тестов, API и (при наличии серверного API) серверного API, диаграммы — в дизайне.
Это наименее спорный набор; подстраивай, когда появится конкретный инструмент.

## Чего не делать

| Не делать | Почему |
| --- | --- |
| Придумывать новые заголовки секций под технику | Ломает валидаторы и привычки проекта |
| Копировать скилл в артефакты | Скилл — инструкция для агента, не содержимое документа |
| Вставлять название инструмента в спеку | Артефакт должен читаться без знания фреймворка |
| Держать два формата одновременно | Один проект — один формат, иначе расходится |
